# 根据主张选择方法

只读取与当前问题相关的部分。以下为选型建议，具体步骤按材料、领域要求和工具可用性确定。

| 主张 | 起点 | 可选方法与工具 | 能支持到哪里 |
|---|---|---|---|
| 事实是否成立 | 规范、原始文件、版本记录、业务记录 | 按对象和时间交叉核对；用 `rg`、Git、SQL、文档检索或一手 API 定位。 | 确认所查范围内的记录或行为；公开承诺与实际行为分别核查。 |
| 形式命题是否成立 | 定义、公理、完整命题、证明和反例 | 推导核查、边界搜索；适用时用 Lean、Coq 或求解器。 | 在所列假设和形式化范围内成立；另核对形式化表达与原问题是否一致。 |
| 机制怎样运行 | 输入输出、源码、配置、执行轨迹、故障现场 | 最小复现、调用追踪、控制输入；用调试器、日志、追踪和性能分析器。 | 观察与机制一致，排除已检查的替代解释；源码状态与实际运行状态要对应。 |
| 某因素是否导致变化 | 处理分配、采集过程、对照与结果资料 | 条件允许时随机实验；否则选择有识别依据的准实验或因果设计，用 Python、R 等估计。 | 在设计和识别假设下支持因果判断；单纯前后对比或相关分析不能直接识别因果。 |
| 能否预测新情况 | 带来源和时间的样本、划分规则、基线 | 留出检验、适合数据结构的交叉验证、时间外推；用评测脚本检查泄漏、误差和分组表现。 | 支持对已测新样本和场景的预测表现；同一人、同一任务或重复记录的泄漏须检查。 |
| 方案能否满足需求 | 真实任务、约束、目标环境和故障条件 | 原型、端到端验证、容量或恢复试验；按需用浏览器、压测、监控和恢复演练。 | 已测要求得到满足，目标用途在已测环境中成立；分别报告模拟与实际条件。 |
| 解释或评价是否合理 | 原作、完整访谈、档案、版本、现场记录 | 细读、版本对照、来源批判、主题分析和反例比较；用标注工具保留位置，适用时独立评议或盲评。 | 解释有材料支持，竞争解释已比较，评价标准和偏好明确；不假设审美有唯一客观答案。 |

## 检查设计的关键假设

量化工作先确认观察单位、分母、测量定义和重复记录。对因果主张，检查分配过程、混杂、时间先后及所选设计的识别条件；对预测主张，检查训练与验证划分、时间信息和场景变化。

比较方案时保留适合任务的基线，可以是现状、简单方案或明确的替代方案。基线、指标和差异标准要说明依据，不能因结果不好而隐去。涉及随机性或测量波动时，按实际需要安排重复测量、随机化或区组，并说明精度。样本量和重复次数依目标差异、变异和成本确定，避免自行指定通用数字。

量化验证要识别哪些合理选择可能改变答案，再做相应敏感性检查。例如，去掉重复记录、改用适当分母、保留缺失值造成的边界、按来源或时间分组。小样本或高度异质材料可能只允许定性结论。

## 学习与解释评价的验证

学习目标拆成具体能力，再用未见题目、独立完成、延迟检验或迁移任务验证。课程产出、讲解流畅和临时通过不能单独说明掌握；所用验证须对应该能力。

定性研究保留上下文、样本选择和编码依据。独立编码或复核可以检查解释稳定性，但是否适用要按研究立场和任务判断，不能把一致率设为所有定性研究的硬门槛。

作品分析先标明版本，区分可回听或回看的结构特征、历史事实、解释和个人评价。让他人按相同材料复查论证时，检验的是材料支持程度及反例处理；审美偏好保留其主体性。

## 混合主张逐项验证

“代码可运行，所以适合真实用户”“成绩上升，所以课程导致提升”“同一批样本表现好，所以能够泛化”都跨越了不同主张。拆开对应证据，分别报告。某个分支不足时缩小结论，不能用另一个分支的通过结果覆盖。
